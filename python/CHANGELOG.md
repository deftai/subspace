# Changelog

## Unreleased

- kernel: `notify()` without params leaves `params` out of the message instead of sending `"params": null`.
- kernel: a handler that raises a `BaseException` that is not an `Exception` (`SystemExit`, `KeyboardInterrupt`) is no longer answered with an internal error; it propagates.
- kernel: the NDJSON decoder skips a UTF-8 byte order mark at the start of the stream.
- kernel: a message that cannot be encoded as JSON (a datetime, a cycle, NaN) no longer vanishes. `NdjsonEncoder.feed()` raises the new `EncodeError` (a `ValueError`) after calling `on_error`; a request fails with `LocalError("send-failed")`, `notify()` raises, and a handler whose answer cannot be encoded replies with an internal error. Later messages still go out.
- kernel: a failed write of an answer is reported as a new `send-failed` diagnostic, not `handler-failed`, and no second answer is attempted.
- kernel: a `cancel_inbound.id` extractor that raises is reported as `invalid-message` instead of closing the connection.
- kernel: `start()` after `close()` does nothing.
- kernel: when the other side ends its stream, `RpcPeer` drains instead of closing at once: outbound requests fail with `closed` and nothing more is read, but request handlers already running may answer for up to `drain_timeout_ms` (new option, default 1000; 0 is the old behaviour) before they are aborted and the peer closes. So `printf '{"id":1,"method":"x"}\n' | agent` gets its answer. `closed`, `on_close` and `is_closed` follow once the drain ends. New `RpcPeer.state`: `idle`, `open`, `draining` or `closed`.
- kernel: when queued writes are still stuck 1 s into `close()`, the peer cancels its writer task, fails those writes with `closed` and aborts the channel. Channels may have an `abort()` (`StreamChannel` aborts its transport); without one, `close()` is called.
- kernel: `TraceTap.note(text, None)` records `"data": null`, as the TypeScript tap does; leave `data` out for a note without data.
- kernel: `MemoryChannel.receive()` may be awaited by several tasks at once; each gets its own item.
- kernel: `SupervisedProcess.exited` and `stop()` return shielded awaitables, so cancelling a wait (e.g. `asyncio.wait_for`) no longer cancels the process's own exit watcher or its stop: a timed-out `stop()` still sends SIGKILL after the grace period, and later calls still work. They are `asyncio.Future`s now, not `asyncio.Task`s.
- kernel: `SupervisedProcess.ended()` settles once the process has exited and its stdout pipe has closed, whether or not anyone read stdout to the end (it hung after `RpcPeer.close()` cancelled the reader). Unread output is still there to read.
- kernel: on POSIX, SIGTERM and SIGHUP now stop live supervised process groups before the process dies of the signal, while groups are alive and only if the app has no handler of its own for that signal (installed from the main thread only).
- kernel: a process group is dropped from the exit-time kill list once its last member is gone, not only if it was gone when its leader exited, so a reused group id is never killed at exit.
- kernel: `stderr_tail_bytes` counts bytes, not characters; a character cut in half at the start of the tail is dropped.
- kernel: on Windows, a command found through PATH and PATHEXT as a `.cmd`/`.bat` file (like `npx.cmd`) is run through cmd.exe (`/d /e:ON /v:OFF /s /c`, so no AutoRun commands such as conda's or clink's can write to stdout) with its arguments escaped as Rust's std escapes them ("BatBadBut", CVE-2024-24576: quoted, quotes doubled, `%` defused), which is safe also for shims that hand `%*` to cmd.exe again; an argument containing CR, LF or NUL is refused with `SpawnError` (code `EINVAL`). The not-found hint mentions .cmd shims.
- kernel: on Windows, `stop()` and the exit-time kill end the child's whole process tree with `taskkill /T` (without `/F` first, then with `/F` after the grace period; the child alone if taskkill cannot run), instead of terminating only the child: a `.cmd` launch's program, a child of cmd.exe, no longer survives and keeps stdout (and `ended()`) open. `stop()` on Windows now waits up to the grace period for a child that ignores the polite request, as on POSIX.
- kernel: `SupervisedProcess(...)` takes a new `stdout_closed` argument; create processes with `spawn_process()`.
- acp: A turn ended by the client after the cancel grace period now drains: queued prompts wait until the agent confirms the old turn (v1: its prompt answer; v2: its idle), for at most twice `cancel_grace_ms`, and its late updates go to the session (`on_idle_update`, `tool_calls`) instead of the next turn. `busy` is False while it drains; a prompt sent then is queued.
- acp: After that drain, the old `session/prompt` request is given up on (`$/cancel_request`) instead of staying pending forever.
- acp: `Session.cancel()` arms the cancel deadline before telling the agent, and tells it in the session's own task: cancelling the caller while it waits no longer leaves the turn without a deadline.
- acp: A tool call id the agent reuses in a later turn belongs to that turn; only background work is routed to earlier turns.
- acp: A client-wide `on_question` answers questions between turns and questions that name no session (they were declined).
- acp: A turn handler that raises `CancelledError`, or a handler task that is cancelled, fails the turn with `RuntimeError("A turn handler was cancelled")`; the turn used to report success.
- acp: Updates for a session closed here are dropped, so a later `load_session` of it no longer replays them.
- acp: `session.modes` is replaced on every change instead of being changed in place.
- acp: `Session.close()` ignores any error from `session/close`, not only RPC and local errors.
- acp: `serve_agent`: with `queue_prompts` on v2, a turn's idle state (and its failed tool calls) now goes out before the next queued turn starts.
- acp: `serve_agent`: a prompt handler that raises now fails the tool calls it left open and stops the terminals it did not detach, as a cancelled turn already did.
- acp: `serve_agent`: a prompt handler that ends with `asyncio.CancelledError` after the turn was cancelled (e.g. it cancelled its own task when `turn.signal` fired) now ends the turn `cancelled`: v1 answers `stopReason: "cancelled"` instead of a -32800 error, and v2 sends its idle state.
- acp: `serve_agent`: a `new_session` that returns the id of a session that is already open is now refused with -32602; before, the open session was replaced and its turn, background work and MCP connections leaked.
- kernel: `AbortSignal.any(...)`: the combined signal can now be `dispose()`d (or used as a context manager) to remove its listeners from the source signals; before, they stayed until a source fired.
- acp: `serve_agent`: a finished turn no longer leaves a listener on the connection's signal (one leaked per turn), and a finished tool call or terminal no longer leaves one on its turn's signal; MCP-over-ACP requests no longer leave one on their server's signal.
- acp: `model_agent`: results of tool calls that ran when a turn hit `max_steps` or was cancelled are no longer dropped: they go to the model with the next prompt, as `PromptInput.tool_results` (new field, default empty).
- acp: `serve_agent(connection_closed=...)`: new optional hook, called with the ids of the sessions still open when the connection closes (`close_session` is still not called for them). `model_agent` uses it to drop those sessions' conversations, which it kept forever before.
- acp: `serve_agent`: on v1, `capabilities={"sessionCapabilities": ..., "mcpCapabilities": ...}` now merge into the advertised ones (as on v2) instead of replacing them, so `close` and `resume` are no longer dropped.
- acp: `serve_agent`: a second `initialize` on a connection is now refused with -32600 (Invalid Request); before, it could switch the protocol mid-connection.
- acp: `AgentTurn.elicit`: an error answer from the client now raises instead of answering `cancel`; only a cancelled turn or a closed connection answers `cancel`.
- acp: `AgentTurn.tool_call(status="completed"|"failed"|"cancelled")` is no longer tracked as open (it was failed again when the turn was cancelled or raised), and `tool_call_update` now keeps v2 background work in step: a create is tracked, and a final status finishes it (a cancellable call finished this way no longer accepts `tool_call/cancel`).
- acp: MCP connections of a session: `session/close`, new servers from load or resume, and a closed connection now abort an MCP connect still in flight (through `McpConnectContext.signal`) instead of waiting for it, up to the connect timeout.
- acp: terminal output is kept as append-only segments instead of one buffer rebuilt per chunk. A `TerminalEvent`'s `terminal` is still a snapshot with the full `output`, but `output` is read from the shared segments when you look (a descriptor on `TerminalState`), so a turn's events no longer each hold a copy (1000 chunks of 4 KB kept 883 MB, now 9 MB). `TerminalState(output=...)`, `==`, `asdict()` and `snapshot()` work as before.
- acp: `ToolCall.snapshot()` no longer copies the content list: the snapshot keeps the list and its length and copies when `content` is read; content chunks append in place (20k chunks: 1.5 s and 1.6 GB kept, now 34 ms). Changing a snapshot's `content` still changes nothing else.
- acp: message, thought and user message events read `text` from the message's log when you look, so events no longer each keep the message so far (40k chunks: 0.7 s and 4 GB kept, now 58 ms). `TextInfo.text` is read the same way. `TurnProjection.text` is cached until a message changes.
- acp: `session.prompt(..., history=...)`: `"all"` (default, unchanged) keeps every event; a number keeps the last that many; `"none"` keeps none. An event is dropped only after every running iteration and the turn's handlers have had it; an iteration started later begins at the oldest event kept. New `TurnHistory` type. `turn.history` returns the kept events.
- acp: `workspace_terminals` keeps output as UTF-8 chunks and decodes it only in `output()` (33k lines past 1 MiB: 2.9 s, now 7 ms). Only a character the limit cut in half is dropped at the start of the kept output; a real U+FFFD there is kept (it was stripped).
- acp: `inside_workspace` and `workspace_files` run their `realpath`/`lstat` checks in a thread instead of on the event loop (with the file read or write, in the same thread).
- acp: endpoint notifications with outbound hooks go through one sender task fed by a queue instead of a task per notification (15k/s to 137k/s through one hook). A notification already going through the hooks is no longer interrupted when its caller is cancelled; one not yet started is still not sent.
- acp: `serve_stdio` writes through one writer thread, in order and whole, with one flush per batch; a cancelled send can no longer interleave frames. Its channel has an `abort()`. `start(trace=...)` buffers the trace file and flushes it 50 ms after a record and on close, instead of a write and flush per message on the event loop.
- kernel: `RpcPeer` writes with a writer task that runs only while something is queued, and skips the middleware runner when there is none. On Python 3.12+ the writer and request handlers start as eager tasks: a write the channel takes at once, and a request handler that does not wait, finish without a trip through the event loop, and a handler runs up to its first `await` before the next message is read. Round trips are about 2x faster on 3.12+. The writer is new on every version, 3.11 included; only eager starts are 3.12+. A loop with a custom task factory (`loop.set_task_factory`) gets normal tasks, made by its factory, since eager tasks would bypass it. On 3.12+ a request handler that raises `SystemExit` or `KeyboardInterrupt` before its first `await` raises it inside the read loop, which ends with it; it still leaves the event loop, as before.
- kernel: once a handler closes the peer, nothing more is dispatched, not even messages already buffered: on 3.12+ such a handler runs inside the read loop, and the next buffered request was dispatched on the closed connection with a `context.signal` that never fired. A request handler started on a closed connection gets an already aborted signal.
- kernel: `RpcPeer.close()` no longer swallows its caller's cancellation while it waits for the reader or a stuck writer to stop: `CancelledError` propagates when the calling task is being cancelled.
- kernel: `trace_tap` copies dicts and lists directly instead of `copy.deepcopy` (other values still go to `deepcopy`); a record still does not change when the message is changed later. About 2x faster per message.
- kernel: the process channel of `spawn_process` has an `abort()` that aborts the stdin transport, so a peer whose child stopped reading drops what is queued instead of keeping the pipe open to write it later.
